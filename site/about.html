About this project

How the judges guide is built

A retrieval-augmented pipeline that turns scattered public records into a sourced voter guide to the 61 judges on the November 2026 Cook County retention ballot. I built it to learn retrieval-augmented generation and LLM evaluation hands-on, on a problem where wrong answers have real costs.

Built by Tricia Scully · Source code on GitHub · Updated

What it does

Retention ballots ask voters to keep or remove dozens of judges, but the evidence about any one judge is spread across a 300,000-row sentencing dataset, three bar associations' websites, a 1 GB campaign-finance file and appellate court opinions. The guide gathers it into one profile per judge:

  • Sentencing compared with what the whole court did for the same charges, with 95% ranges
  • Bar association ratings and the attorney feedback behind them, quoted word for word
  • Career background: former prosecutor, criminal defense, work for vulnerable clients
  • Campaign money by donor type, and where donor organizations give elsewhere
  • Appellate track record: how often the judge's rulings were affirmed or reversed (in progress)

The design rule throughout: every claim on the page points to a verbatim quote or a computed number with its uncertainty. The language model never writes text readers see; it extracts facts from retrieved documents, and code verifies them.

How it works as a retrieval-augmented system

For each judge, the pipeline retrieves the relevant documents, gives them to a language model as its only context, has it return structured facts with a quote for each, then verifies every quote in code before anything reaches the page. It follows the standard RAG loop (retrieve, augment, generate) with an added verification stage, because a voter guide can't tolerate invented facts.

  1. Retrieve. Each judge is the query. Bar evaluations are retrieved by a name matcher that handles middle initials, nicknames, hyphenated and married surnames, and typos on source pages. Appellate opinions come from Boolean full-text search on CourtListener, then a filter that parses each opinion's caption to confirm the judge presided. Campaign filings are retrieved by streaming a 1 GB file and keeping each judge's committees.
  2. Augment. The retrieved document goes into the prompt as the model's only source, with instructions to use nothing else and to copy evidence word for word. Output is constrained to a JSON schema compiled into a grammar, so it can't come back malformed.
  3. Generate. A local model, Qwen3-Coder-Next running through llama.cpp on a laptop, extracts the facts. The same code can call Claude through the Anthropic API, so the two can be compared on the same evaluation.
  4. Verify. Each quote must appear verbatim in the source, a flag needs wording that shows the fact, and reader-facing text comes from templates. The page cannot contain a sentence the model invented.

Retrieval here is lexical and structured rather than embedding-based, because every document is keyed to a known judge. Semantic search over the opinions is the next phase.

How the output is evaluated

Four layers of checks each caught different errors:

  • Grounding: is every evidence quote verbatim in the source? Catches invented or paraphrased evidence.
  • Hand labels: a tuning set and a separate held-out set, labeled from the text alone under a written guide. Catches real quotes with the wrong label, which grounding can't.
  • Outside data: every judge with 100+ criminal sentences in court records must have criminal-court experience. This exposed a schema bug that cost recall on 5 of 11 judges, fixed with one prompt sentence.
  • Support check: a stronger model judges whether each quote supports its label (built, ready to run with an API key).

Lessons from building it

  • Prompts set what the model attempts; code decides what counts. Across five prompt versions, stricter rules made the model dump facts into catch-all buckets or loop until it hit the output limit. Splitting the job (the model extracts broadly, code checks keep only verified facts) took precision to 1.00.
  • A local model was good enough. A quantized mixture-of-experts model on a 64 GB laptop extracted each judge in about 9 seconds, at no cost.
  • Every source had data-quality problems. Sentence dates as far off as 2921, names stored "Last, First" or in capitals, misspellings on source pages, a dataset that silently stopped in 2024. Each was found by checking outputs against expectations.
  • Rate limits shaped retrieval. With search capped at 50 requests an hour, the pipeline batches judges per query, caches every result page, and waits out limits on the server's terms.

Responsible design

  • No voting recommendations; the guide shows the records and how to read them.
  • Every number carries its uncertainty, and specialty-court judges are flagged so they aren't compared unfairly.
  • Donors are shown by employer and organization, never by individual name.
  • Readers' ballot choices stay in their own browser.
